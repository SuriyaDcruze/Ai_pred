# Release v0.6.0 — Conversation Intelligence Engine

- **Tag:** `v0.6.0-conversation-intelligence`
- **Date:** 2026-07
- **Sprint:** 6 (COMPLETE)
- **Highlights:** the **Conversation Intelligence Engine** — ask AEGIS, in natural language, to
  **explain** an existing prediction / its evidence / confidence / history / similar cases / learning
  / system status. A **read-only** layer over the Decision Intelligence Engine; the LLM **explains
  only**. Deterministic, honesty-gated, traceable.

Builds on `v0.5.0-decision-intelligence`. Adds a new conversational layer **additively** — nothing
about how predictions are made, resolved, stored, retrieved, learned from, or composed changes.
Distinct from the legacy `app/chat/` assistant (ADR 0029/0030), which is untouched.

## Overview
A 7-module pipeline (`app/conversation/`) — **Conversation Engine → Intent Detection → Retrieval
Orchestrator → Prompt Builder → LLM Adapter** — served at `/chat/*`. It consumes **only** the Decision
Intelligence Engine (never the prediction models), imports neither the Prediction nor the Outcome
engine, and gives **no advice and no predictions** — where information does not exist it says
`INSUFFICIENT_DATA` / `NOT_AVAILABLE` / `NOT_SUPPORTED`.

## New capabilities
- **Conversation domain model** (`models.py`, `cnv-1`): messages, sessions (frozen, checksummed),
  context, citations, serialization.
- **Intent Detection** (`intent.py`, `int-1`): deterministic rule-based classifier (no LLM/embeddings)
  + extensible registry + entity extraction + validation.
- **Retrieval Orchestrator** (`retrieval.py`/`sources.py`, `ret-1`): retrieves **only through**
  Decision Intelligence via a transport-independent source; availability handling; verbatim merge.
- **Prompt Builder** (`prompt.py`, `prm-1`): deterministic, fixed-order prompt; explain-only system
  prompt; citation formatting + missing-citation rejection; token budgeting. Never invents content.
- **Conversation Engine** (`engine.py`, `eng-1`): in-memory sessions; lifecycle state machine;
  multi-turn memory + follow-up handling.
- **LLM Adapter** (`llm_adapter.py`, `llm-1`): provider-independent (`EchoProvider` stub +
  `OpenAIProvider`/`azure_openai`, duck-typed client, **no SDK import**); normalised errors.
- **REST API** (`/chat/*`, `app/api/chat.py`): `POST /chat/message`, `POST /chat/session`,
  `GET`/`DELETE /chat/session/{id}`, `GET /chat/health`, `GET /chat/version`.

## Architectural changes
- **Six ADRs** (0029–0034): Conversation Intelligence Engine; legacy-chat coexistence; LLM provider
  abstraction; retrieval-through-DI-only; prompt determinism; thin REST transport.
- **Read-only + explanation-only**: imports neither engine; no writes; no migration.
- **Honesty preserved**: absent data reported honestly; missing citations rejected; no fabrication.

## API additions
- Six `/chat/*` endpoints (above). Responses carry the assistant text + session id + conversation
  status + availability status + citations + version metadata. Error taxonomy: `400` bad request ·
  `404` unknown session · `409` closed/duplicate · `429` LLM rate-limited · `503` provider/deps
  unavailable · `500` internal (LLM error categories mapped, **never** leaked). Full OpenAPI.

**Sprint 1–5 interfaces are unchanged** — `/forward/*`, `/memory/*`, `/memory/similar*`,
`/learning/*`, `/intelligence/*`, the Prediction/Outcome/Risk engines, `predictions`, every prior
table, and the legacy `POST /chat` all behave exactly as before. Integration point: the conversation
layer consumes the Decision Intelligence Engine (Sprint 5) read-only.

## Breaking changes
**None.** All changes are additive: a new package, a new router (one `include_router` line), and the
version bump `0.5.0` → `0.6.0`. One backward-compatible internal fix: the Sprint 6 M5 lifecycle table
now allows `CREATED → COMPLETED/EXPIRED` (so a just-created session can be closed) — all M5 tests
unchanged. No existing endpoint, table, engine, migration, or the legacy `POST /chat` changes.

## Migration / upgrade notes
No action required. `/chat/*` composes everything **in memory / on read** from existing data; nothing
is created or migrated. Without a configured LLM provider the `EchoProvider` returns a clearly-marked
stub; enable real explanations by supplying a provider client (`app.state.conversation_llm`). On
today's near-empty corpus, explanations honestly report `INSUFFICIENT_DATA` until Forward Testing
accumulates a record.

## Known limitations
- No live LLM by default (offline stub); a real provider needs a thin client translator + credentials.
- In-memory sessions (per-process; no persistence).
- **Explanation only — no predictive edge, no advice.** Consistent with `docs/RESULTS.md`, the only
  verified edge remains the Outcome Engine (backtest-only). This layer explains existing evidence; it
  manufactures no edge.

## Future roadmap
Wire a real LLM provider; feed the live corpus; a conversation UI; optional session persistence; and,
in a later sprint, reconcile/supersede the legacy `app/chat/`.
